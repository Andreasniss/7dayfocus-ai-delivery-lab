# P11 Android Personal Install: Specification

- **Owner:** Andreas
- **Accepted:** 2026-09-01
- **Status:** Accepted for implementation

## Product requirements

1. The packaged Android application provides the current local-first seven-day planner and browser-local persistence.
2. Fixture planning remains deterministic and requires no account, credential, network request, or external service.
3. The Android assistant does not display Anthropic, OpenAI, or OpenRouter as available providers.
4. The UI explains that live-provider mode remains available only in local web development with the loopback gateway.
5. Proposal generation remains non-mutating; one complete validated proposal is applied only after explicit approval.
6. Import, export, reset, touch interaction, and small-screen behavior remain part of the device-test contract.

## Technical requirements

- Use Tauri v2 with the existing React/Vite production bundle.
- Use the stable identifier `com.nissenlabs.dayfocus` from the earlier prototype.
- Target Android API 36 for the current Google Play submission requirement and keep the Tauri minimum at API 24.
- Request only the Android `INTERNET` permission generated by the Tauri shell; fixture mode itself makes no external request.
- Keep Tauri capabilities at `core:default`; add no filesystem, shell, HTTP, notification, or credential plugin.
- Detect the packaged runtime at the UI boundary and pass an explicit provider capability into the assistant.
- Do not call the local `/api/plan` path from the packaged application.
- Keep signing configuration external and ignored.

## Mobile device test

On Andreas's personal phone, record:

1. installation and launch;
2. add, edit, complete, prioritize, move, and delete;
3. persistence after app restart;
4. fixture proposal generation, diff review, explicit approval, and stale-proposal rejection;
5. import/export and reset or their documented Android WebView limitation;
6. portrait layout, touch drag behavior, keyboard focus, and error states;
7. offline relaunch after the first successful installation; and
8. reinstall/update behavior where relevant.

## Alternatives considered

### Installable PWA

This is the smallest packaging path, but it requires a deployed HTTPS application and does not reuse the already tested Android Studio/Tauri learning. It remains a parked reviewer-hosting option under P07.

### Capacitor

Capacitor would also package the web application, but it introduces a second mobile stack without a demonstrated advantage for this fixture-only personal install.

### Native Android

A native rewrite would maximize Android-specific learning but duplicate the validated TypeScript domain and materially exceed the project's completion goal.

## Accepted design

Reuse Tauri v2. Keep the mobile build deliberately fixture-only until a separate accepted design provides a safe native network boundary. This is the smallest path that preserves current behavior, earlier learning, and inspectable controls.

## Concerns and human gates

- Android WebView file download/upload behavior must be verified on the real phone.
- A physical device and Android toolchain are required before installation can be claimed.
- Andreas controls USB debugging, installation approval, keystore creation, Play App Signing, disclosures, and any Play Console submission.
- A Play production path may be blocked by account-specific closed-testing requirements. That is an accepted stop condition.
